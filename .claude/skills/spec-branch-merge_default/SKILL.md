# /spec-branch-merge — Слияние веток тикетов в mergeBranch + проверочная сборка

Текущая рабочая копия (`/workspace/project`) уже зачекаучена на **mergeBranch**
(`<тикеты>-to-release/{version}` — детерминированное имя от состава тикетов и версии
релиза, формируется конвейером сборки; пример: `AO-xxx_AO-yyy_...-to-release/01.012.00`).
Эта ветка уже создана и запушена на origin конвейером сборки до запуска этого скилла.
Скилл **не делает** ни `git checkout -b`, ни `git push` для mergeBranch ни в какой
момент — всё, что здесь происходит, остаётся локальным коммитом на уже существующей
ветке.

Задача — по очереди влить в mergeBranch переданные ветки тикетов, аккуратно разрешая
конфликты; затем прогнать проверочную сборку (стек определяется автоматически по
файлам-маркерам в корне worktree), исправляя выявленные ею ошибки минимальными правками;
и завершиться **локальным коммитом без `git push`** — финальный пуш merge-ветки и
открытие PR `mergeBranch` → `release/{version}` берёт на себя конвейер сборки после
маркера `AO_TASK_DONE`.

Все перечисленные в `--branch=...` ветки **уже зафетчены конвейером сборки в этот worktree**
перед запуском скилла — конвейер делает это аутентифицированным запросом к хостингу,
у агента токен для доступа к хостингу не передаётся. Повторный fetch в этом скилле не
нужен и не выполняется. Если ветка всё-таки не разрешается как `origin/<branch>` — это
значит, что fetch конвейера упал, ошибка уже зафиксирована на его стороне, и оператор
разбирается с причиной. Никакого собственного fallback на «угадать» нет.

Этот скилл **никогда не пушит** ни в `mergeBranch`, ни в `release/{version}`, ни в
`mainBranch`. Любой `git push` в нём — ошибка, не задача.

Ветки переданы по имени, не по ссылке на PR, — конвейер уже знает имя ветки каждого
тикета и передаёт его напрямую. Скилл не делает ни одного запроса к REST API хостинга
(gitverse/GitHub/Bitbucket) и ни одного fetch — вся работа только через локальный git.

**Использование:**
`/spec-branch-merge --merge-branch=<имя mergeBranch> --branch=<имя ветки 1> [--branch=<имя ветки 2> ...]`
— `--merge-branch` обязателен (это та ветка, на которой уже зачекаутен worktree, и в которую
нужно вливать); `--branch` перечислены в порядке, в котором их нужно вливать (раньше в
списке = вливается раньше).

## Влить ветки по очереди (локально, без push)

Для каждой `--branch=` ветки, в переданном порядке:

1. `git merge --no-edit origin/{branch}`
2. Если конфликтов нет — коммит слияния уже создан автоматически, переходи к следующей ветке.
3. Если возник конфликт:
    - Открой каждый конфликтующий файл и пойми **оба** намерения — что изменил тикет, чью ветку
      сейчас вливаешь, и что уже накопилось в текущей ветке от ранее влитых тикетов. Не выбирай
      слепо "ours"/"theirs" — сохрани оба содержательных изменения, если они не противоречат друг
      другу по смыслу (например, независимые правки в разных частях одного файла, обе версии
      которых нужны).
    - Если изменения действительно взаимоисключающие (правят одну и ту же логику по-разному) и
      корректно разрешить конфликт без риска сломать код нельзя — не гадай: `git merge --abort`,
      затем `AO_TASK_FAILED` с точным описанием, какая ветка и какие файлы конфликтуют и в чём суть
      конфликта, чтобы человек мог разрешить его вручную.
    - Если конфликт разрешён — `git add` изменённых файлов, `git commit` (без `--no-edit`, дефолтное
      merge-сообщение подходит).

## Проверочная сборка (перед завершением)

Скилл остаётся универсальным — он ничего не знает о составе модулей проекта, в котором запускается.
Стек сборки определяется автоматически по наличию файлов-маркеров в корне worktree. Сборка
выполняется **один раз** (после слияния всех веток); если она упала — фиксированное число
попыток fix-and-retry в этом же ходе.

1. Определи, какие проверочные команды применимы к текущему репозиторию, по наличию файлов
   в корне worktree:
    - `pom.xml` → добавить `mvn -B -q -DskipTests verify` (полная multi-module Maven-сборка
      без тестов; `-q` ограничивает шум в логе, `-DskipTests` — это именно сборка, а не прогон
      тестов);
    - `package.json` со скриптом `build` (в `package.json` присутствует ключ `"build": "..."`)
      → добавить `npm --silent run build`;
    - `Makefile` со строкой вида `^build:` (цель `build`) → добавить `make -s build`;
    - `Cargo.toml` → добавить `cargo check`;
    - `go.mod` → добавить `go build ./...`.
      Команды собираются в shell-строку через `&&` в указанном порядке (порядок фиксирован,
      чтобы поведение было детерминированным при наличии нескольких маркеров). Перед запуском
      выведи отдельной строкой `BUILD CHECK: <полная команда>` — для прозрачности в логе.
2. Если ни один маркер не найден — этот шаг пропускается без сообщения (для проектов без
   явной команды сборки это валидный кейс, а не ошибка), переходи сразу к завершению.
3. Выполни получившуюся команду (`bash -c "<команда>"` или эквивалент через `&&`-объединение).
   Если код возврата 0 — переходи к завершению.
4. Если код возврата не 0 — прочитай последние ~50 строк лога ошибки, определи, какие файлы
   правки затронуты. Внеси **минимально необходимые** правки: не рефакторь ничего «по дороге»,
   не правий смежные файлы, если они не виноваты в ошибке, не меняй зависимости/версии без
   явной причины в логе, не делай `git revert` ранее влитых веток (это разрушительная операция,
   выкидывающая чужой merge-коммит).
5. `git add` изменённых файлов + `git commit -m "fix: resolve merge breakage detected by build check"`.
   Не используй `--no-edit`, merge-сообщение тут неуместно.
6. Повтори п. 1–п. 3 (заново пересобери команду по маркерам — на случай, если что-то
   добавилось/удалилось — и снова запусти).
7. Если за 5 итераций сборка не стала зелёной — `git merge --abort` **не делай** (ветки уже
   слиты, откатываться некуда; для диагностики перед `AO_TASK_FAILED` выполни
   `git log --oneline -10`). Выведи `AO_TASK_FAILED` с описанием: какая команда упала,
   последняя ошибка, какие файлы правил, на какой итерации остановился.

Между итерациями **не используется кеш сборки** — каждый запуск делает «честную» сборку с нуля,
на случай, если предыдущая ошибка была как раз из-за неполной очистки артефактов.

## Завершение

По завершении работы (все ветки успешно влиты, проверочная сборка прошла или была
пропущена) выведи в отдельной строке ровно `AO_TASK_DONE` — это сигнал конвейеру сборки,
что пора делать финальный `git push origin HEAD:{mergeBranch}` и открывать Pull Request
`mergeBranch` → `release/{version}`. Скилл обязан завершиться с локальным коммитом (или
цепочкой merge/fix-коммитов), но без `git push`. Если что-то из вышеперечисленного не
удалось — выведи `AO_TASK_FAILED`. Ничего не пиши после этой строки.
