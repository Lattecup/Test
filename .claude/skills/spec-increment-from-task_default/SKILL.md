# /spec-increment-from-task — Завести инкремент по описанию задачи

Эта команда получает **сырой текст** — название и описание тикета — и сама создаёт новый файл
инкремента с нуля, а затем доводит его до полноценного плана (шаги 1-3 ниже), но
**останавливается перед реализацией кода**: реализация в pipeline-конвейере задач — отдельный
шаг с валидацией человека между планом и кодом (см.
`specification/absolut/03-tasks/business.md#кнопки-конвейера-pipeline-actions`).

**Использование:** `/spec-increment-from-task
в PDF на странице задачи. Нужно...`

Если у задачи уже есть `specification/increment/{раздел}/{ticket}/intent.md` (AO-152 — задача прошла
необязательный этап "Формирование намерения") — остаток текста после флагов не нужен: скилл сам
возьмёт содержимое intent.md как входные данные.

## Шаг 0. Разобрать аргументы, найти intent.md (если есть) и создать файл инкремента

AO-313 — `--release=` стал опциональным: задачу можно создать и без явной привязки к релизу.
«Разделом» файла инкремента считается либо `--release=<version>` (например `01.014.00`), либо
`develop` (если `--release=` не передан). Дальше в тексте скилла этот раздел обозначается как
`{раздел}` — `{release}` для обычного случая, `develop` для задач без зафиксированного релиза.
Полный путь к файлу — `specification/increment/{раздел}/{ticket}/increment.md`.

`--ticket=` **обязателен всегда** — из него берётся ключ тикета (часть пути) и проверка
уникальности. Никаких других источников для `{ticket}` нет (парсить ветку, угадывать по
контексту и т.п. — ошибка). `--release=` берётся либо из флага, либо (если флага нет) по
умолчанию считается пустым и путь строится через `develop/`. В этом случае ровно одна и та же
папка `develop/{ticket}/` создаётся независимо от того, сколько раз вызвали команду, — а
перенос артефактов в `{release}/{ticket}/` (если релиз в итоге был задан) делает уже скилл
`/spec-increment-actualize` на стадии `SPEC_ACTUALIZATION` (см. его шаг «Перенос артефактов»).
При автоматическом pipeline-запуске `TaskPipelineServiceImpl.execute` подставляет флаги сам:
если у задачи `releaseId` есть, вшивает `--release=<version>`, если нет — `--release=` опускается
целиком. При ручном вызове человек тоже может опустить флаг.

1. Извлеки `--release=` (если есть) и `--ticket=` (обязателен) из начала `$ARGUMENTS`. Если
   `--ticket=` отсутствует — остановись и сообщи об ошибке (не пытайся угадать/вычислить его
   откуда-то ещё, включая `git branch --show-current`). Если `--release=` отсутствует — это
   нормальный путь (AO-313), `{раздел}` = `develop`. Остаток текста после удаления флагов —
   запасной вариант входного текста (см. пункт 3).
2. **Сначала попробуй найти `intent.md` в папке тикета**: `specification/increment/{раздел}/{ticket}/intent.md`
   (AO-152 — необязательный этап "Формирование намерения" записывает результат работы скилла
   `spec-intent-generation` именно в этот файл, и когда он есть, бизнес-контекст в нём уже
   дистиллирован — лучше строить план сразу от него, чем разбирать сырой текст тикета):
   - **Файл найден и непуст** — используй его содержимое как входной текст тикета для всех
     дальнейших шагов (шаги 1-3а ниже). Остаток `$ARGUMENTS` из пункта 1 игнорируется — он
     замещён intent'ом, перенос дополнительного сырого текста поверх дистиллированного намерения
     испортил бы итоговый план.
   - **Файла нет** — переходи к пункту 3.
3. **Фолбэк на остаток `$ARGUMENTS`** (когда intent.md отсутствует — обычный путь через
   `OPEN → SPEC_DEVELOPMENT` или ручной запуск): используй остаток текста после удаления флагов
   как входной текст тикета. Если текст пуст или не осмыслен — остановись и попроси пользователя
   уточнить, что нужно сделать, вместо того чтобы создавать пустой/бессмысленный инкремент. В этом
   случае `task.incrementNumber` уже может быть проставлен backend'ом на `{ticket}`, хотя файл ещё
   не создан — если пользователь позже уточнит задачу и файл будет создан по тому же ключу, поле
   останется корректным; если задачу отменят/переформулируют, поле можно поправить вручную
   (`specification/increment/01.000.00/30/30-increment-number-editable.md`).
4. Создай файл `specification/increment/{раздел}/{ticket}/increment.md`, содержимое на этом шаге —
   выбранный в пункте 2 или 3 входной текст без изменений (это черновик, как если бы его руками
   положил человек). Дальше с ним работают шаги 1-3а ниже.

`task.incrementNumber` уже проставлен backend'ом равным `{ticket}` до старта этого скилла
(`TaskPipelineServiceImpl.execute` — при переходе на "Разработку спецификации") — печатать номер
инкремента отдельным маркером не нужно, такого маркера больше нет.

## Шаг 1. Прочитать контекст

1. `specification/increment/{раздел}/index.md` (список тикетов этого раздела — релиза или
   develop-зоны, если раздел уже существует) — нет ли уже пересекающегося инкремента внутри
   того же раздела; `specification/index.md` — общая навигация по разделам, помогает понять,
   к какому разделу проекта ближе всего относится задача
2. Релевантные разделы `specification/absolut/` (auth/projects/tasks/agents/git/docs/admin/
   infrastructure/pipline) — актуальное состояние "как есть", с которым план должен состыковаться
3. Затронутый код (controller → service → repository → entity → dto для backend; соответствующие
   компоненты/api для frontend) — пойми реальные сигнатуры, а не предполагай их

## Шаг 2. Задать уточняющие вопросы

Свободный текст тикета почти никогда не содержит всех деталей, нужных для реализации. Прежде чем
писать план, определи неоднозначности и задай уточняющие вопросы пользователю (через
`AskUserQuestion`, а если вопросов много и они не укладываются в закрытые варианты — обычным
текстом). Типичные зоны неопределённости:

- Границы изменений (что явно НЕ входит в объём)
- Роли/права доступа к новой функциональности
- Поведение при ошибках и граничных случаях
- Совместимость с уже существующими данными/поведением (нужна ли миграция, что с уже
  существующими записями)
- Если текст тикета — по сути просто SQL/конфиг без описания UI или API — нужен ли
  соответствующий контроллер/UI, или изменение чисто в данных

Если таких вопросов с закрытым набором вариантов набралось несколько — задавай их по одному, не
все сразу в одном ответе: сформулируй один вопрос, дождись ответа пользователя и только потом
переходи к следующему. У headless-исполнения (когда этот скилл запущен pipeline-стадией) вопрос с
вариантами передаётся текстовым маркером `AO_QUESTION`, который парсится и рендерится в чате
ровно один раз за ход — несколько вопросов в одном ответе не превратятся в несколько отдельных
меню с радиобаттонами, второй и далее потеряются или сломают разбор первого.

Не переходи к шагу 3, пока не получены ответы на все существенные вопросы.

## Шаг 3. Переписать файл инкремента по правилам проекта

Правила формата инкрементов в этом проекте (см. примеры исторических инкрементов под
`specification/increment/01.000.00/`):

```markdown
# Инкремент {ticket} — Название

## Статус

К выполнению

## Контекст

[Как это устроено сейчас, почему требуется изменение — 1-3 абзаца со ссылками на конкретные
классы/методы/таблицы]

## Решения по ходу реализации

[Только если в тексте тикета или в уточняющих вопросах были открытые развилки — фиксируй принятое
решение и краткое обоснование. Пропускай раздел, если всё однозначно с самого начала]

## Цель

[Конкретное, проверяемое описание результата — нумерованный список или таблица]

## Изменения в коде

[По слоям/файлам: БД-миграция → backend (entity/repository/service/controller/dto/mapper) →
frontend. Для каждого файла — что меняется, с примерами сигнатур/сниппетов где это проясняет
намерение]

## Совместимость

[Если есть уже существующие данные/поведение, на которые изменение влияет — что с ними
происходит. Пропускай раздел, если неприменимо]

## Затронутые файлы

[Плоский список путей — заполнится по факту реализации, когда запустится разработка]
```

Статус остаётся `К выполнению` — этот файл только что появился, реализация ещё не начиналась.

## Шаг 3а. Обновить трёхуровневый индекс и застейджить

Индекс инкрементов — три уровня вложенности, каждый — только заголовок и список ссылок (без
обзорного текста):

- `specification/increment/index.md` — список **разделов** (релизов и `develop`), ссылки на
  `{раздел}/index.md`. Для develop-зоны строка одна и та же:
  `| [develop](../develop/index.md) | Задачи без зафиксированного релиза | В работе |`.
- `specification/increment/{раздел}/index.md` — список **тикетов** этого раздела, ссылки на
  `{раздел}/{ticket}/index.md`
- `specification/increment/{раздел}/{ticket}/index.md` — список **файлов** этого тикета (на этом
  шаге — только что созданный `increment.md`; `spec-intent-generation`/`increment-review` могут
  добавить в эту же папку `intent.md`/`review-report.md` до или после этого шага — не удаляй ссылки
  на файлы, которых сейчас не видишь в контексте этого шага, а которые уже могут быть в папке,
  проверь `Glob` перед перезаписью)

1. Если `specification/increment/{раздел}/index.md` не существует — создай его и добавь строку в
   `specification/increment/index.md` (если раздела там ещё нет):
   - Для релиза: `| [{release}](../{release}/index.md) | Релиз {release} |`.
   - Для develop: `| [develop](../develop/index.md) | Задачи без зафиксированного релиза | В работе |`.
   Если оба файла уже существуют — не трогай их, если строка для `{раздел}`/`{ticket}` уже есть.
2. Добавь (или создай) `specification/increment/{раздел}/{ticket}/index.md`: заголовок `# {ticket}`
   и список ссылок на файлы, реально существующие в папке (`Glob specification/increment/{раздел}/{ticket}/*.md`
   на момент этого шага) — как минимум `increment.md`.
3. Добавь строку в конец `specification/increment/{раздел}/index.md`: `| [{ticket}](./{ticket}/index.md) | Название | К выполнению |`
   — `Название` бери из заголовка `# Инкремент {ticket} — Название`, записанного на шаге 3. Не трогай
   остальные строки.
4. `git add` все затронутые файлы (сам файл ещё не коммитится — это делает пользователь или
   следующий шаг pipeline-конвейера; но он должен быть виден в `git status`/`git diff` как
   staged-новый, а не просто лежать untracked на диске):
   ```bash
   git add "specification/increment/{раздел}/{ticket}/increment.md" \
           "specification/increment/{раздел}/{ticket}/index.md" \
           "specification/increment/{раздел}/index.md" \
           "specification/increment/index.md"
   ```

`specification/increment/index.md` и `specification/increment/*/index.md` слиты через git
`merge=union` (`.gitattributes`), поэтому параллельное добавление строк разными тикетами/релизами
сливается автоматически без конфликта. Если конфликт всё же возник (например, слияние выполняется
стороной, не учитывающей `.gitattributes`) — разрешать его, оставляя строки **обеих** сторон, не
выбирая одну.

## Шаг 4. Сообщить результат

Не реализуй код и не запускай `mvn`/`npm` — это задача следующего шага pipeline-конвейера (человек
проверяет план, затем кнопкой конвейера отдельным запуском стартует реализацию).

Сообщи пользователю:
- Путь созданного файла инкремента (`specification/increment/{раздел}/{ticket}/increment.md`)
- Краткое резюме плана (цель, ключевые файлы)
- Что дальше — человеку нужно провести ревью инкремента (проверить план в файле), после чего
  кнопкой конвейера запускается разработка

## Важно

- Не начинай реализацию, пока не закрыты уточняющие вопросы из шага 2, и не начинай её вообще —
  эта команда только заводит и дооформляет план
- Не трогай файлы **других** тикетов — ни исторических (`Статус: Выполнено`), ни соседних
  "К выполнению". Единственное исключение — `specification/increment/index.md` и
  `specification/increment/{раздел}/index.md`: в них на шаге 3а добавляется ровно одна новая
  строка (в конец таблицы), существующие строки не трогаются
- Один вызов — один новый инкремент; не пытайся угадать, что пользователь имел в виду несколько
  задач сразу, если текст тикета описывает что-то одно связное
- Никогда не определяй `{release}`/`{ticket}` самостоятельно (парсингом ветки, догадкой по
  контексту и т.п.) — только из явных флагов `--release=`/`--ticket=` в `$ARGUMENTS`. Если
  `--release=` не передан, `{раздел}` = `develop`, не пытайся его «додумать» из чего-либо ещё

## Маркер завершения (для запуска из pipeline)

По завершении работы выведи в отдельной строке ровно
`AO_TASK_DONE` (если всё удалось) или `AO_TASK_FAILED` (если не удалось выполнить). Ничего не
пиши после этой строки.
