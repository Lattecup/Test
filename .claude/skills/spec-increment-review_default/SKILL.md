# /spec-increment-review — Ревью инкремента без правок кода

Полностью локальное ревью текущей ветки относительно базовой: сборка, тесты/lint и ручной разбор
diff на предмет багов. Код не меняется — единственный результат работы с файловой системой это
отчёт в `specification/increment/{раздел}/{ticket}/review-report.md`.

**Использование:** `/spec-increment-review --release=01.003.00 --ticket=AO-8 master` |
`/spec-increment-review --release=01.003.00 --ticket=AO-8 develop` |
`/spec-increment-review --ticket=AO-8 develop`

`$ARGUMENTS` — флаг `--ticket=` (обязателен) и опциональный `--release=` (AO-313: если не передан,
артефакты кладутся в `develop/{ticket}/`); backend вшивает флаги в промпт при автоматическом
pipeline-запуске тем же способом, что и для `spec-increment-from-task`. После флагов — имя **уже
существующей локально** ветки (или другого ref), с которой сравнивается текущая ветка. Если
`--ticket=` отсутствует — остановись и сообщи об ошибке, не пытайся определить ticket каким-то
другим способом (включая имя текущей ветки).

## Строгие ограничения

- **Не переключай ветки.** Ни `git checkout`, ни `git switch`, ни `git worktree add` на другую
  ветку. Скилл работает строго в том состоянии рабочей копии, в котором был запущен, включая
  незакоммиченные изменения, если они есть.
- **Не обращайся к удалённому репозиторию.** Ни `git fetch`, ни `git pull`, ни `git push`, ни
  запросы к API Gitverse. Если базовая ветка из аргумента отсутствует локально — останови
  выполнение и сообщи об этом пользователе, не пытайся её получить.
- **Не исправляй код.** Даже очевидные однострочные баги — этот скилл только читает код и пишет
  отчёт.

## Шаг 0. Разобрать аргументы, определить {раздел} и проверить окружение

1. Извлеки `--release=` (если есть) и `--ticket=` (обязателен) из начала `$ARGUMENTS`. Если
   `--ticket=` отсутствует — остановись и сообщи об ошибке, не пытайся его вычислить (включая имя
   текущей ветки).
2. AO-313 — `--release=` стал опциональным: задачу можно ревьюить и без зафиксированного релиза.
   «Разделом» файла инкремента считается либо `--release=<version>` (например `01.014.00`), либо
   `develop` (если `--release=` не передан). Дальше в тексте скилла этот раздел обозначается как
   `{раздел}` — `{release}` для обычного случая, `develop` для задач без зафиксированного релиза.
   Полный путь к плану/отчёту — `specification/increment/{раздел}/{ticket}/`.
3. Остаток `$ARGUMENTS` после удаления флагов — имя базовой ветки/ref для сравнения.
4. `git rev-parse --abbrev-ref HEAD` — определить текущую ветку. Если HEAD в состоянии detached —
   сообщи пользователю и уточни контекст, прежде чем продолжать.
5. `git rev-parse --verify --quiet refs/heads/<базовая ветка>` — убедиться, что базовая ветка есть
   локально (если это не ветка, а тег/коммит — проверь соответствующим способом). Нет — стоп,
   попроси пользователя получить её вручную (`git fetch`/`git branch`); сам этого не делай.
6. `git status --short` — зафиксировать, есть ли незакоммиченные изменения. Они входят в объём
   ревью наравне с закоммиченными.

## Шаг 1. Найти план инкремента и подготовить diff

1. `BASE=$(git merge-base <базовая ветка> HEAD)`
2. Список изменённых файлов: `git diff --name-only $BASE` (сравнение с рабочим деревом — включает
   незакоммиченные изменения поверх HEAD)
3. Полный diff для чтения: `git diff $BASE` (при большом объёме — читай по файлам/группам файлов)
4. Найди план инкремента по уже известным `{раздел}`/`{ticket}`:
   `specification/increment/{раздел}/{ticket}/increment.md`.
   - **Файл существует** — используй его как план для сверки.
   - **Файла нет** — сверяться с планом будет не с чем, ревью в шаге 4 опирается только на код; всё
     равно продолжай (это не повод останавливать ревью).
5. "Название инкремента" — заголовок `# Инкремент {ticket} — Название` файла плана, если он найден;
   иначе спроси у пользователя короткое название для отчёта.

## Шаг 2. Сборка и тесты backend

Если среди изменённых файлов (шаг 1.2) есть пути из `backend-core/`, `agent-manager/`,
`task-tracker/` или корневого `pom.xml`:

```bash
mvn clean install
```

При большом количестве модулей допустимо ограничиться изменёнными модулями и их потребителями
(`mvn -pl <модули> -am clean install`), но при любых сомнениях — полная сборка.

Зафиксируй: успех/провал, список упавших тестов и мест компиляционных ошибок с ключевыми строками
(не весь лог целиком).

Если backend не затронут — шаг пропускается, в отчёте явно отмечается "backend не затронут,
сборка не запускалась".

## Шаг 3. Lint и сборка frontend

Если среди изменённых файлов есть пути из `frontend-core/`:

```bash
cd frontend-core
npm run lint
npm run build
```

Зафиксируй результат каждой команды отдельно — lint может упасть при успешном build, и наоборот.

Если frontend не затронут — шаг пропускается аналогично, с явной пометкой в отчёте.

## Шаг 4. Ручное ревью diff

Прочитай каждый изменённый файл **целиком**, а не только hunks из diff — контекст вокруг
изменений часто скрывает баг, не видимый в самом diff. Сверяйся с планом инкремента из шага 1.4,
если он найден. Ищи корректностные баги — то, что реально ломается на конкретных входных
данных/состояниях, а не стилистические предпочтения:

- Логические ошибки, гонки состояний, неверные условия
- Расхождения с планом инкремента (заявленное поведение не реализовано или реализовано иначе)
- Мёртвый код / ветки, которые никогда не выполняются (например, эффект или callback, который
  фактически не срабатывает)
- Крайние случаи, допустимые по типам, но ломающие логику (пустые списки, null, повторный клик,
  первый рендер до загрузки данных и т.п.)

Каждую находку подтверждай чтением реального кода — не сообщай о баге, в котором не уверен на
100% после перепроверки. Второстепенные замечания (упрощение, переиспользование, эффективность)
выноси отдельным списком с пометкой "не блокирует", не смешивай их с багами.

## Шаг 5. Сформировать отчёт

Путь: `specification/increment/{раздел}/{ticket}/review-report.md`.

Если файл уже существует (повторный запуск после правок по замечаниям через
`spec-repair-review-fails`) — мержи новые замечания, **не перезаписывая** прошлые. Якорь для
сопоставления — `{путь}:{строка}:{signature}`, где `signature` — первые ~80 символов
нормализованного текста из `**Проблема:**` (без пробелов по краям и переносов). Якорь пишется в
`<!-- id: … -->` HTML-комментарии сразу под `### N. …` — это позволяет переносить/перенумеровывать
пункты, не ломая матчинг.

Конкретный протокол мержа:

1. Сначала прочитай существующий `review-report.md` целиком.
2. Составь список уже зафиксированных замечаний (по якорям) со статусами `✅ исправлено …` /
   `🚫 вне scope этого скилла` / `⚠️ требует ручной проверки` — эти трогать нельзя, переноси их в
   новый отчёт как есть.
3. Для каждой новой находки проверь: если якорь совпал с уже зафиксированной — обнови статус
   (например, новое ревью нашло, что «исправленная» правка что-то сломала → `⚠️ требует ручной
   проверки` вместо `✅`); иначе добавь новый раздел `### N+1. …` в конец `## Находки` /
   `## Второстепенные замечания`.
4. Секции `## Сборка и тесты`, `## Изменённые файлы`, `## Итог` всегда переписывай заново — они
   описывают только текущий прогон. `## Итог` пересобери с учётом перенесённых статусов из п. 2.
5. Если существующего файла нет — пиши отчёт с нуля по шаблону ниже.

Это не нарушает правило "не перезаписывать файлы `specification/increment/`" из `CLAUDE.md`:
то правило — про исторические планы инкрементов (`increment.md`), а `review-report.md` — рабочий
журнал ревью, который накапливает историю замечаний между прогонами `spec-increment-review` и
`spec-repair-review-fails`.

Обнови также `specification/increment/{раздел}/{ticket}/index.md`, добавив ссылку на
`review-report.md`, если её там ещё нет (не удаляй существующие ссылки — `Glob` папки перед правкой,
как в шаге 3а `spec-increment-from-task`).

Шаблон:

```markdown
# Отчёт ревью — {ticket}: {Название инкремента}

**Ветка:** `{текущая ветка}` → `{базовая ветка}` (merge-base `{короткий SHA}`)
**Раздел:** `{раздел}` (release `{release}` либо `develop`)
**Дата:** {дата}
**Незакоммиченные изменения в момент ревью:** да/нет

## Сборка и тесты

### Backend
{✅ Успех / ❌ Провал / ⏭ Пропущено — backend не затронут}

[при провале — список упавших тестов/ошибок компиляции]

### Frontend
- Lint: {✅ / ❌ / ⏭}
- Build: {✅ / ❌ / ⏭}

[при провале — ключевые строки ошибок]

## Изменённые файлы

{вывод git diff --name-only $BASE}

## Находки

### 1. {Краткое название бага}
<!-- id: {путь}:{строка}:{первые ~80 символов нормализованного **Проблема:**} -->
**Файл:** `{путь}:{строка}`
**Проблема:** {что не так}
**Сценарий:** {конкретные входные данные/состояние → неверный результат}

[...]

Если багов не найдено: "Багов, ломающих корректность, не найдено."

## Второстепенные замечания

{список, не блокирует; или "нет"}

## Итог

{Готово к мержу / Требует доработки} — {краткое обоснование}
```

## Шаг 6. Перенос артефактов из `develop/` под релиз (AO-313)

Этот шаг выполняется **только** если `{раздел}` = `develop` — то есть задача была создана без
зафиксированного релиза и все её артефакты до сих пор лежат в develop-зоне.

Цель — если к моменту ревью у задачи уже известен релиз, перенести папку `develop/{ticket}/` под
этот релиз, чтобы индексы и навигация были в обычном виде. Конкретный релиз НЕ берётся из
`{ticket}` или из имени ветки — только из текущего состояния задачи (например, из
`task_metadata.releaseId`, если он там уже есть, либо спросить у пользователя).

Подробный протокол переноса — по аналогии с шагом 6 скилла `spec-increment-actualize`:

1. Узнай у пользователя, есть ли у задачи релиз на текущий момент. Если пользователь не уверен
   или релиз не назначен — задача **остаётся в `develop/`**, никакого автопереноса в фиктивный
   релиз не делается (флаг остаётся за человеком, и develop-зона продолжает жить рядом с релизами
   как «задачи без зафиксированного релиза»). В этом случае шаг 6 просто завершается без действий.
2. Если релиз назначен, выполни `git mv specification/increment/develop/{ticket}/ specification/increment/{release}/{ticket}/`
   для всех файлов в папке (`increment.md`, `intent.md` если есть, `index.md` тикета, `review-report.md`).
   Если `git mv` по какой-то причине не сработал (например, файлы ещё не закоммичены) — используй
   обычный `mv` + последующий `git add`.
3. В `specification/increment/index.md` строка про develop-зону остаётся на месте (другие
   develop-задачи ещё могут там жить). Не удаляй её.
4. В `specification/increment/develop/index.md` удали **только** строку про этот `{ticket}`
   (остальные develop-задачи не трогай). Если develop-зона после этого оказалась пустой — удали и
   саму папку `develop/` целиком вместе с её `index.md`.
5. В `specification/increment/{release}/index.md` добавь в конец таблицы строку про перенесённый
   тикет (если её ещё нет): `| [{ticket}](./{ticket}/index.md) | Название | К выполнению |` —
   `Название` бери из заголовка `# Инкремент {ticket} — Название` в перенесённом `increment.md`.
6. `git add` все изменённые индексы и перенесённые файлы. Сам коммит — на усмотрение
   пользователя / следующего шага pipeline.
7. После переноса **путь к файлу отчёта для дальнейших действий — уже
   `specification/increment/{release}/{ticket}/review-report.md`**, а не develop.

## Шаг 7. Сообщить пользователю

Кратко (2-4 предложения): результат сборки/lint, число найденных багов, путь к файлу отчёта (с
учётом переноса из шага 6, если он был). Не дублируй содержимое отчёта в чат целиком — файл уже
содержит все детали.

## Важно

- Код не меняется ни при каких обстоятельствах — этот скилл только читает код и пишет отчёт.
- Ничего не коммить и не пуш — отчёт (и, возможно, перенесённые артефакты из шага 6) остаются
  незакоммиченными файлами в рабочей копии, решение о коммите за пользователем.
- Не используй `git checkout`/`git switch`/`git worktree add` на другую ветку и любые команды,
  обращающиеся к origin (`fetch`/`pull`/`push`/API Gitverse).
- Если сборка/lint не запускались из-за отсутствия изменений в соответствующей части — это не
  находка и не блокирует итоговый вердикт.

## Маркер завершения (для запуска из pipeline)

По завершении работы выведи в отдельной строке ровно
`AO_TASK_DONE` (если всё удалось) или `AO_TASK_FAILED` (если не удалось выполнить). Ничего не
пиши после этой строки.
