# /spec-increment-actualize — Актуализировать абсолютную спецификацию по инкременту

Финальный шаг жизненного цикла инкремента: код уже реализован и прошёл ревью — эта команда
приводит `specification/absolut/` (описание системы "как есть") в соответствие с тем, что реально
изменилось, и закрывает сам файл инкремента (`Статус: Выполнено`). Если артефакты инкремента
лежат в develop-зоне (задача создавалась без зафиксированного релиза), а целевой релиз известен —
команда заодно переносит их из `develop/` под этот релиз.

**Использование:**
```
/spec-increment-actualize --release=01.023.00 --ticket=<KEY>
/spec-increment-actualize specification/increment/01.023.00/<KEY>/increment.md   # shorthand
/spec-increment-actualize <KEY>                                                  # shorthand
/spec-increment-actualize 01.023.00/<KEY>                                        # shorthand
```

## Разбор аргументов

| Флаг | Описание |
|------|----------|
| `--release=<ID>` | Номер релиза (например `01.023.00`). Помимо поиска файла — целевой релиз для переноса артефактов из `develop/` (шаг 6). |
| `--ticket=<KEY>` | Ключ тикета (строка вида `{БУКВЫ}-{ЦИФРЫ}`). |

Если переданы оба флага — путь: `specification/increment/{release}/{ticket}/increment.md`.

Позиционная форма (shorthand): `<путь к increment.md>`, `<TICKET>` или `<RELEASE>/<TICKET>` — поиск через `Glob specification/increment/<...>/<TICKET>/increment.md`.

## Правила структуры `specification/absolut/` (не зависят от конкретного проекта)

- `specification/absolut/index.md` — только заголовок и список ссылок на `index.md` каждого
  раздела. Никакого обзорного текста, никаких деталей — просто навигация.
- Каждый раздел — отдельная папка `specification/absolut/{N}-{слаг}/`. Внутри — `index.md`
  (только заголовок раздела и список ссылок на файлы внутри этой папки — без описания/обзора) и
  файлы с содержанием: как правило `db.md` (схема БД), `business.md` (бизнес-логика, роли, правила,
  статусы), `api.md` (эндпоинты, DTO, коды ошибок) — но если часть материала не укладывается ни в
  одну из этих трёх тем (инфраструктура, деплой, интеграция с внешним сервисом, конфигурация CI и
  т.п.), для неё создаётся отдельный файл с содержательным именем, а не искажаются db/business/api.
- Каждый файл раздела (кроме index.md) начинается с `[← Назад](index.md)`.
- Номера разделов не переиспользуются и не сдвигаются — новый раздел получает
  `максимальный существующий номер + 1`.
- Файл раздела — не резиновый: если после актуализации он длиннее 300 строк, раздели его на
  вложенный подраздел — папку с `index.md` и файлами-подразделами (протокол в шаге 3).

## Шаг 0. Найти файл инкремента

Инкременты хранятся по пути `specification/increment/{раздел}/{ticket}/increment.md`, где
`{раздел}` — релиз либо `develop` (задача без зафиксированного релиза).

Если `$ARGUMENTS` — существующий путь (заканчивающийся на `increment.md`), используй его
напрямую. Иначе воспринимай аргумент как:
- **номер тикета** (например `<KEY>`) — ищи через `Glob specification/increment/*/{ticket}/increment.md`
  (звезда — любой раздел: релиз или `develop`)
- **релиз/тикет** (например `01.023.00/<KEY>`) — ищи через `Glob specification/increment/{release}/{ticket}/increment.md`

Несколько кандидатов или ни одного — покажи список и уточни у пользователя.

Найденный путь запомни как «исходный путь» — на шаге 6 может понадобиться перенос файлов из
`develop/` под конкретный релиз.

## Шаг 1. Понять, что изменилось

1. Прочитай файл инкремента целиком — разделы "Изменения в коде" и "Затронутые файлы" описывают,
   что сделано
2. Если в файле есть раздел "Обоснование решений по результатам разработки" — прочитай и его: там
   причины конкретных решений (отступления от плана, выбор между альтернативами, обход
   неочевидного поведения), которых нет ни в самом плане, ни в дифе кода. Раздела нет — это
   нормально, значит на разработке не было решений, которые стоило объяснять отдельно
3. Если "Затронутые файлы" пуст, неполон или расходится с реальностью — проверь фактическое
   состояние кода/репозитория (например, `git diff`/`git log` для этого инкремента, если история
   это позволяет), не доверяй плану вслепую
4. Разложи изменения по природе: схема БД (миграции/таблицы) — одно, HTTP/WS API (контроллеры,
   DTO) — другое, бизнес-правила/поведение/роли/статусы — третье, всё остальное (инфраструктура,
   конфиги, скиллы автоматизации, интеграции) — отдельно

## Шаг 2. Определить раздел(ы) `specification/absolut/`

1. Прочитай `specification/absolut/index.md` — список существующих разделов
2. Для каждого раздела, который может быть релевантен, прочитай его `index.md` (список файлов) и,
   при необходимости, `business.md`/`api.md`/`db.md` — пойми предметную область раздела по
   содержанию, а не по названию папки
3. Сопоставь затронутый инкрементом код с предметной областью разделов. Один инкремент может
   затрагивать несколько разделов одновременно (например, БД-миграцию в одном разделе и API в
   другом) — актуализируй каждый затронутый раздел
4. Если ни один существующий раздел не подходит по смыслу — создай новый:
   - номер = максимальный существующий номер папки `specification/absolut/*/` + 1
   - слаг и название раздела — по смыслу предметной области, в стиле уже существующих разделов
     этого проекта (посмотри их названия и папки, чтобы выдержать стиль)

Не переходи к шагу 3, если не уверен, к какому разделу отнести изменения, — лучше уточни у
пользователя, чем угадай и создай дублирующий/неверный раздел.

## Шаг 3. Обновить/создать файлы раздела

Для каждого целевого раздела:

1. Точечно обнови только то, что реально изменил инкремент — не переписывай файл целиком и не
   трогай факты, к инкременту не относящиеся. Но если в редактируемом файле встретился факт,
   который больше не соответствует коду, — исправь или удали его: устаревшее не должно
   соседствовать с актуальным
2. `db.md` — таблицы/колонки/индексы/миграции; `api.md` — эндпоинты, роли доступа, DTO, коды
   ошибок; `business.md` — бизнес-правила, роли и права, статусы, доменная логика и её причины
3. Если часть изменений не укладывается ни в одну из этих тем — создай/обнови отдельный файл с
   содержательным именем (не `misc.md` — конкретное имя темы, например `deploy.md`)
4. Пиши только факты из кода/файла инкремента — не придумывай и не обобщай сверх того, что видишь
5. Не сохраняй малозначительные детали, которые тривиально читаются из кода: полные перечни
   полей/методов, сигнатуры, бесхитростный CRUD. Документируй смысл — правила, ограничения, роли,
   причины, контракты между модулями; конкретная форма (какие поля у DTO, какие аргументы у
   метода) и так видна в коде. Вопрос-фильтр: «что потеряет читатель, если этого факта здесь не
   будет?» Ничего — не пиши
6. Причины из раздела "Обоснование решений по результатам разработки" (шаг 1.2), если он был —
   вплетай рядом с фактом, который они объясняют (обычно в `business.md`), а не отдельным блоком
   и не как есть. Переноси только то, что объясняет неочевидное текущее поведение, и формулируй
   в настоящем времени как свойство системы («X делает Y, потому что Z»), а не как историю
   принятия решения
7. Устройство юнит-тестов (фикстуры, моки, структура тест-классов, покрытие) в абсолютную
   документацию не переносится. Если поведение, которое проверяет тест, важно — опиши его как
   поведение системы (обычно в `business.md`), без упоминания самих тестов

### Если файл раздела вырос длиннее 300 строк

После правок проверь длину каждого изменённого тобой файла раздела. Перевалил за 300 строк —
раздели его на вложенный подраздел, а не оставляй расти:

1. Создай рядом папку `{name}/` (по имени исходного файла), разложи содержание по смысловым темам
   в 2+ файлов с содержательными именами, исходный `{name}.md` удали.
2. `{name}/index.md` — только заголовок темы, `[← Назад](../index.md)` и список ссылок на
   файлы-подразделы (тот же принцип, что у `index.md` раздела).
3. Каждый файл-подраздел начинается с `[← Назад](index.md)`.
4. В `index.md` раздела замени ссылку `{name}.md` → `{name}/index.md`.

Вложенность держи в один уровень: файлу-подразделу, снова превысившему лимит, лучше создать
соседний файл по теме, чем ещё одну вложенную папку.

## Шаг 4. Актуализировать `index.md` раздела

Для каждого затронутого (или только что созданного) раздела `specification/absolut/{раздел}/index.md`
должен содержать **только**:

```markdown
# Название раздела

[← Назад](../index.md)

## Содержание

- [API](api.md)
- [Бизнес-логика](business.md)
- [База данных](db.md)
```

Список — ссылки на файлы, которые **реально существуют** в этой папке сейчас (включая любые
дополнительные файлы из шага 3, не только эти три). Если в файле уже была секция вида "Обзор" с
описательным текстом — удали её: разрешено только название раздела и список ссылок.

## Шаг 5. Актуализировать `specification/absolut/index.md`

Тот же принцип — **только** заголовок и список ссылок на `index.md` всех разделов:

```markdown
# [Название проекта/спецификации]

## Содержание

1. [Название раздела 1](01-slug/index.md)
2. [Название раздела 2](02-slug/index.md)
```

Если создан новый раздел — добавь для него строку в конец списка. Не переписывай формулировки
существующих строк, если их раздел не менялся в этом инкременте.

## Шаг 6. Перенос артефактов из `develop/` под релиз

Этот шаг выполняется **только** если исходный путь из шага 0 указывает на
`specification/increment/develop/{ticket}/` — то есть задача была создана без зафиксированного
релиза и все её артефакты до сих пор лежат в develop-зоне. Исходный путь уже указывает на
конкретный релиз — пропусти шаг.

Цель — перенести папку `develop/{ticket}/` под конкретный релиз, чтобы индексы и навигация
были в обычном виде. Релиз для переноса берётся в порядке приоритета:

1. **`--release=<version>` из `$ARGUMENTS`** — приоритетный источник: если флаг передан,
   используй его сразу и **не спрашивай** пользователя.
2. **Спросить пользователя** — крайний случай: флага нет. Если пользователь не уверен или релиз
   не назначен — задача **остаётся в `develop/`**, никакого автопереноса в фиктивный релиз не
   делается (develop-зона продолжает жить рядом с релизами как «задачи без зафиксированного
   релиза»).

Конкретный релиз НЕ берётся из `{ticket}` или из имени ветки — только из перечисленных выше
источников.

Подробный протокол переноса (после того как релиз определён):

1. Выполни `git mv specification/increment/develop/{ticket}/ specification/increment/{release}/{ticket}/`
   для всех файлов в папке (сам `increment.md`, `intent.md` если есть, `index.md` тикета). Если
   `git mv` по какой-то причине не сработал (например, файлы ещё не закоммичены) — используй
   обычный `mv` + последующий `git add`.
2. В `specification/increment/index.md` поправь строку этого тикета: замени `develop/{ticket}` на
   `{release}/{ticket}` в тексте и пути ссылки —
   `- [{release}/{ticket}]({release}/{ticket}/index.md)`. Позицию строки в списке не меняй.
3. `git add` перенесённые файлы и изменённый индекс. Сам коммит — на усмотрение пользователя /
   следующего шага конвейера.
4. После переноса **исходный путь для всех дальнейших шагов этого скилла — уже
   `specification/increment/{release}/{ticket}/`**, а не develop. Шаги 7-9 ниже работают с
   перенесёнными файлами.

## Шаг 7. Завершить инкремент

Если `Статус` файла инкремента ещё не `Выполнено`:
1. `Статус` → `Выполнено`
2. Дополни/уточни "Затронутые файлы" фактическим списком — код и документация вместе

## Шаг 8. Проставить метку SDD в Jira

Проставить на тикет маркер SDD после закрытия статуса.

1. Ключ тикета — последний сегмент пути файла инкремента.
2. Если доступен скилл `spec-sdd-label` и есть его конфигурация Jira (YAML
   `jira-sdd-label-config.yml` рядом с `scripts/jira-sdd-label-1.0.0.jar` или env
   `GIGA_JIRA_*`) — вызови `/spec-sdd-label <ticket>`. Креды передавать как CLI-аргументы
   запрещено.
3. При любом сбое Jira **не блокируй** закрытие инкремента: выведи
   `⚠️ Не удалось проставить метку SDD на <KEY>: <reason>. Закрытие инкремента продолжается,
   метку можно поставить вручную позже.` и переходи к шагу 9.

`spec-sdd-label` не пробрасывает исключения — любые сбои (включая отсутствие конфигурации)
превращает в exit code 1 и не блокирует actualize.

## Шаг 9. Сообщить результат

Сообщи пользователю: какие разделы актуализированы (существующие — какие именно файлы; новый —
номер, название, состав файлов), что статус инкремента закрыт, и что произошло с меткой SDD
(поставлена / пропущена из-за недоступности скилла / предупреждение о сбое Jira). Если исходный
путь был в develop-зоне — сообщи судьбу артефактов: перенесены под релиз (старый и новый пути)
или остались в `develop/`, потому что целевой релиз не определён.

## Важно

- Пиши только факты из кода/инкремента — не придумывай
- Актуализируй точечно: не трогай факты, не относящиеся к текущему инкременту и остающиеся
  верными. Но устаревшее (не соответствующее текущему коду) удаляй или исправляй, даже если в
  этот инкремент оно не входит, — в актуальной документации ему нет места
- Абсолютная спецификация фиксирует фактическое состояние системы и не хранит историческую
  справку. Не пиши в формате "было/стало" ("до этого было X, теперь Y", "раньше здесь
  использовался..."), не указывай, когда и в каком инкременте/релизе что появилось или менялось.
  Причина неочевидного поведения — уместна, история её появления — нет: «X делает Y, потому что
  Z», а не «сначала делали Z, потом перешли на Y»
- Не сохраняй малозначительную информацию, которую легко понять из кода (полные перечни полей и
  сигнатур, бесхитростный CRUD): документация отвечает «почему и зачем», код — «как именно»
- Не описывай устройство юнит-тестов — фикстуры, моки и структура тест-классов не часть
  абсолютной документации
- Не переименовывай и не перенумеровывай существующие разделы
- Целевой релиз для переноса артефактов из `develop/` (шаг 6) не определяй самостоятельно —
  только флаг `--release` или явный ответ пользователя; не угадывай его по ключу тикета или
  имени ветки
- В БД-описаниях приоритет у реальных имён колонок (snake_case или аналог), а не у имён полей в
  коде приложения
- Не привязывайся к конкретным названиям разделов/технологиям — определяй структуру по
  фактическому состоянию `specification/absolut/`, а не по памяти о конкретном проекте
- Раздел "Обоснование решений по результатам разработки" в файле инкремента (если есть) — не
  переноси в абсолютную документацию дословно и отдельным блоком, а вплетай по факту рядом с
  соответствующим поведением (шаг 3.6); его отсутствие в файле инкремента — не пропуск, а сигнал,
  что объяснять было нечего

## Маркер завершения

По завершении работы выведи в отдельной строке ровно
`AO_TASK_DONE` (если всё удалось) или `AO_TASK_FAILED` (если не удалось выполнить). Ничего не
пиши после этой строки.
