# /spec-increment-implement — Реализовать код по готовому инкременту

Выполняет **только реализацию** кода по уже готовому плану — план уже написан и провалидирован
человеком (pipeline-статус "Ревью инкремента"), уточняющие вопросы уже закрыты. **Не трогает**
`specification/absolut/`,
`specification/index.md`, `specification/increment/index.md` и вложенные
`specification/increment/*/index.md`/`specification/increment/*/*/index.md`, и не меняет `Статус`
файла инкремента — актуализация документации и финальный статус `Выполнено` относятся к отдельному,
более позднему этапу конвейера ("Запустить актуализацию абсолютной документации").

**Использование:** `/spec-increment-implement specification/increment/01.003.00/AO-8/increment.md` |
`/spec-increment-implement AO-8`

## Шаг 0. Найти файл инкремента

Если `$ARGUMENTS` — существующий путь, используй его напрямую; иначе воспринимай аргумент как ключ
тикета и ищи `specification/increment/*/{ключ}/increment.md` через `Glob` (звезда — релиз, он
заранее неизвестен; AO-313 — это может быть и `develop/`, если задача создавалась без релиза). Несколько кандидатов или ни одного — покажи список и уточни у пользователя.
Исторические инкременты (заведённые до этой схемы) лежат под
`specification/increment/01.000.00/{ключ или номер}/` — файл там может называться не `increment.md`,
а сохранять историческое имя (`Glob specification/increment/01.000.00/{ключ}/*.md`, если первый
поиск не дал результата).

Если `Статус` найденного файла уже `Выполнено` — сообщи об этом и остановись: реализовывать
нечего.

## Шаг 1. Прочитать план и контекст

1. Файл инкремента целиком — план уже готов, вопросы закрыты. Если в файле остались явные
   заглушки/открытые развилки без решения — не додумывай их сам молча, остановись и уточни у
   пользователя
2. Релевантные разделы `specification/absolut/` — актуальное состояние "как есть", с которым план
   должен состыковаться (читаем, **не пишем**)
3. Затронутый код (controller → service → repository → entity → dto для backend; соответствующие
   компоненты/api для frontend) — реальные сигнатуры, а не предположения

## Шаг 2. Реализовать

Строго по разделу "Изменения в коде" файла инкремента, соблюдая конвенции `CLAUDE.md`:

- Слоистая архитектура: `controller/api/` → `controller/` → `service/api/` → `service/` →
  `repository/` → `mapper/` → `entity/` → `dto/`
- Все entity наследуют `BaseEntity`
- MapStruct-мапперы: `@Mapper(componentModel = "spring")`
- Миграции БД — Liquibase (`changelog-master.xml` + SQL-файл с formatted SQL header)
- После реализации — прогони проверки:
  ```bash
  mvn -pl <изменённый-модуль> test
  npm run lint    # если менялся frontend-core
  npm run build   # если менялся frontend-core
  ```
- Если реальность разошлась с планом — точечно поправь разделы "Изменения в коде"/"Совместимость"
  файла инкремента (не переписывай план целиком). Если расхождение существенное (меняет объём или
  подход) — остановись и уточни у пользователя, а не переизобретай план молча

## Шаг 3. Написать/поправить backend-тесты

Если инкремент затронул backend-контроллеры — вызови скил `/backend-integration-tests`:

- **Новые эндпоинты** (новый метод контроллера или новый контроллер, появившийся в рамках этого
  инкремента) — напиши на них интеграционные тесты.
- **Изменившиеся эндпоинты** (логика сервиса/валидация/права доступа существующего метода
  контроллера поменялась в рамках этого инкремента) — поправь под новое поведение существующие
  тесты этого метода, не переписывай их с нуля.
- **Не пиши тесты на контроллеры/эндпоинты, которых этот инкремент не касается** — даже если по
  пути заметил, что они недопокрыты.
- **Не переписывай существующие тесты на логику, которая не менялась** — ни в затронутом
  контроллере, ни тем более в соседних.

Если инкремент не трогал backend-контроллеры (только frontend, только миграции без нового
эндпоинта и т.п.) — шаг пропускается.

После — прогони тесты изменённого модуля ещё раз (`mvn -pl <модуль> test`), чтобы убедиться, что и
новые/поправленные тесты, и весь остальной существующий набор проходят.

## Шаг 4. Заполнить "Затронутые файлы" и застейджить

1. Замени содержимое секции "Затронутые файлы" файла инкремента на плоский список реально
   изменённых/созданных путей — это код и сам файл плана, документации здесь нет
2. `git add` все изменённые/новые файлы кода и сам файл инкремента. `specification/absolut/`,
   `specification/index.md`, `specification/increment/index.md` и вложенные индексы
   (`specification/increment/*/index.md`, `specification/increment/*/*/index.md`) не трогай и не
   стейджи — они не менялись
3. `Статус` файла инкремента **не меняй** — он остаётся `К выполнению`

## Шаг 5. Зафиксировать обоснования решений (если есть)

По ходу реализации могли приниматься решения, которых нет в исходном плане и которые не очевидны
из самого кода: выбор между альтернативами, компромисс из-за ограничения, обнаруженного только на
практике, осознанное отступление от плана, обход неочевидного поведения зависимости/фреймворка.
Если такое было — допиши это в конец файла инкремента отдельным разделом:

```markdown
## Обоснование решений по результатам разработки

- {что решено не так, как в плане, или не описано планом} — {почему именно так}
```

- Пиши только то, что реально несёт причину ("почему"), а не пересказ того, что уже и так видно из
  раздела "Изменения в коде" или из самого диффа. "Реализовал метод X" — не обоснование, это
  пересказ; "Метод X не использует Y, потому что Z" — обоснование.
- Если за всю реализацию не было ни одного решения, которое стоит объяснять отдельно от кода — не
  создавай этот раздел вообще. Пустой или формальный раздел ("всё сделано по плану", "особых
  решений не было") хуже, чем его отсутствие: отсутствие раздела однозначно читается как "нечего
  добавить", а не как забытый шаг.
- Раздел — последний в файле, после всех существующих секций плана.

## Шаг 6. Сообщить результат

Сообщи пользователю: что реализовано (кратко), какие файлы изменены, какие тесты написаны/поправлены
(если применимо), результат прогона тестов/lint/build. Явно укажи, что `specification/absolut/` не
актуализирована — это отдельный следующий шаг конвейера.

## Важно

- Не задавай уточняющих вопросов о том, ЧТО делать, — план уже провалидирован; уточняй только при
  прямом противоречии между планом и реальным кодом, которое нельзя разрешить безопасным умолчанием
- Не трогай `specification/absolut/`, `specification/index.md`, `specification/increment/index.md`
  и вложенные `specification/increment/*/index.md`/`specification/increment/*/*/index.md`
- Не меняй `Статус` файла инкремента на `Выполнено`
- Не трогай файлы **других** инкрементов
- Тестами (новыми или поправленными) покрывай только контроллеры/эндпоинты, реально затронутые
  этим инкрементом — не другие, и не переписывай тесты на логику, которая не менялась
- Раздел "Обоснование решений по результатам разработки" — только для реальных причин, не для
  пересказа сделанного; нет значимого решения — нет и раздела

## Маркер завершения (для запуска из pipeline)

По завершении работы выведи в отдельной строке ровно
`AO_TASK_DONE` (если всё удалось) или `AO_TASK_FAILED` (если не удалось выполнить). Ничего не
пиши после этой строки.
