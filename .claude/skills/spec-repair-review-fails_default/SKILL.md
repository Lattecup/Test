# /spec-repair-review-fails — Исправить замечания из отчёта ревью

Скилл читает `specification/increment/{раздел}/{ticket}/review-report.md`, для каждого замечания
со статусом «не исправлено» вносит точечную правку в код, прогоняет сборку в затронутых модулях и
при зелёной сборке помечает замечание как исправленное. По завершении выводит `AO_TASK_DONE`
(или `AO_TASK_FAILED` при неустранимой ошибке/непрохождении тестов).

**Использование:** `/spec-repair-review-fails --release=01.003.00 --ticket=AO-8` |
`/spec-repair-review-fails --ticket=AO-8`

`$ARGUMENTS` — обязательный флаг `--ticket=` и опциональный `--release=` (AO-313: без `--release=`
артефакты лежат в `develop/{ticket}/`). backend вшивает флаги в промпт при автоматическом
pipeline-запуске тем же способом, что и для `spec-increment-review`. Если `--ticket=` отсутствует —
остановись и сообщи об ошибке, не пытайся определить ticket каким-то другим способом (включая имя
текущей ветки).

## Строгие ограничения

- **Не правь `specification/absolut/**`, `intent.md`, `increment.md`, `index.md` тикета.** Эти
  файлы — либо владение других шагов конвейера, либо плановая документация, не предмет правки
  этого скилла. Если замечание из отчёта указывает на раздел `specification/absolut/` — пометь
  замечание как «вне scope этого скилла» (см. формат статусов ниже) и заверши `AO_TASK_DONE`:
  такие правки делает отдельный шаг `spec-increment-actualize`.
- **Не коммить и не пушь.** Промежуточные правки кода остаются в рабочей копии как
  незакоммиченные изменения. Решение о коммите и PR — за пользователем / следующим шагом
  конвейера (кнопка «Запустить ревью агента повторно» или «Передать на ревью человеку»).
- **Не переключай ветки.** Ни `git checkout`, ни `git switch`, ни `git worktree add` на другую
  ветку. Скилл работает в текущей ветке, в которой был запущен.
- **Не обращайся к удалённому репозиторию.** Ни `git fetch`, ни `git pull`, ни `git push`, ни
  запросы к API Gitverse/GitHub/Gitea. Если замечание требует данных с remote — пометь его как
  «требует ручной проверки» и заверши `AO_TASK_FAILED`.

## Шаг 0. Разобрать аргументы и проверить окружение

1. Извлеки `--release=` (если есть) и `--ticket=` (обязателен) из начала `$ARGUMENTS`. Если
   `--ticket=` отсутствует — остановись и сообщи об ошибке.
2. AO-313 — `--release=` опционален: «разделом» считается либо `--release=<version>`, либо
   `develop`. Полный путь к отчёту ревью — `specification/increment/{раздел}/{ticket}/review-report.md`.
3. Прочитай обязательно:
   - `specification/increment/{раздел}/{ticket}/review-report.md` — список замечаний со статусами
   - `specification/increment/{раздел}/{ticket}/increment.md` — план инкремента, чтобы понимать
     контекст правок
   - `.claude/conventions/index.md` и его секции (shared/java/typescript) — правила, которым
     должны соответствовать правки
4. `git rev-parse --abbrev-ref HEAD` — определить текущую ветку. Если HEAD в состоянии detached —
   сообщи пользователю и остановись (`AO_TASK_FAILED`).
5. `git status --short` — зафиксировать, есть ли уже незакоммиченные изменения. Если есть и они
   не относятся к правкам из этого скилла — остановись (`AO_TASK_FAILED` с понятным сообщением:
   «перед запуском закоммитьте или откатите текущие незакоммиченные изменения, иначе их авторство
   смешается с правками скилла»). Наличие изменений от самого скилла (правки, внесённые ранее
   в этом же запуске) — нормально.
6. Найди `mvn` (или `mvnw`) в PATH. Зафиксируй `git diff --name-only HEAD` как стартовый
   baseline — он понадобится на шаге 3, чтобы понять, какие файлы реально менял скилл, и
   определить, какие модули пересобирать.

## Шаг 1. Каталог замечаний

1. Прочитай `review-report.md` целиком. Если файл отсутствует — заверши `AO_TASK_DONE` без
   правок: исправлять нечего, отчёта нет.
2. Найди все замечания в разделах `## Находки` и `## Второстепенные замечания`. Замечание
   выглядит как подзаголовок (`### 1. ...`) с последующими строками `**Файл:**`, `**Проблема:**`,
   `**Сценарий:**` (формат — из шага 5 `spec-increment-review`).
3. Для каждого замечания определи его текущий статус:
   - **Не исправлено** — в строках под `### N. ...` нет маркера исправления (формат маркера —
     см. шаг 4).
   - **Исправлено** — в строке под `### N. ...` есть маркер `✅ исправлено <дата>` (или просто
     `✅`).
   - **Вне scope** — маркер `🚫 вне scope этого скилла <обоснование>`. Такие замечания оставлены
     по решению скилла как «требуют другого шага», повторно их не трогай.
   - **Требует ручной проверки** — маркер `⚠️ требует ручной проверки <обоснование>`. Не правь
     код по такому замечанию, оставь маркер как есть.
4. Собери список замечаний со статусом «Не исправлено» и отсортируй их по `path:line` (или по
   номеру `### N.`). Если список пуст — заверши `AO_TASK_DONE` без правок (нечего править).

## Шаг 2. Внести правки

Для каждого замечания из списка шага 1.4:

1. Прочитай реальный код в указанном `path:line` (через `Read`, не только из diff). Замечания
   могут устаревать (diff старый, файл уже переехал) — если строка/файл изменились, найди
   ближайший эквивалент по смыслу замечания и обнови ссылку в `**Файл:**` соответственно.
2. Внеси точечную правку минимального объёма, исправляющую именно ту логику, на которую указано
   в `**Проблема:**`. Не выходи за рамки замечания — никаких «по дороге поправлю ещё одну штуку».
3. Если правка невозможна без нарушения одного из «Строгих ограничений» (правка в
   `specification/absolut/`, требует обращения к remote, требует смены ветки, требует
   глобального рефакторинга) — не правь код, а пометь замечание как «вне scope» (шаг 4).
4. Если правка требует решений, которые не покрыты планом инкремента и не очевидны из кода
   (например, выбор между двумя API-дизайнами) — пометь замечание как «требует ручной проверки»
   и заверши по нему работу на этом запуске. Не угадывай.

## Шаг 3. Прогнать сборку

1. Определи список затронутых модулей по файлам, изменённым в шаге 2 (а также файлам, которые
   скилл тронул по сравнению с baseline из шага 0.6): для каждого Java-файла возьми его
   Maven-модуль по `pom.xml` ближайшего предка; для фронтенд-файлов — `frontend-core/`.
2. Прогони `mvn clean install -pl <модули> -am -DskipTests=false` (полная сборка с тестами
   только для затронутых модулей). При большом числе модулей и сомнениях — лучше полная
   `mvn clean install` (как в `spec-increment-review`).
3. Если сборка **упала** из-за правки этого скилла — откати ровно эту правку (`git checkout
   HEAD -- <изменённые файлы>`) и пометь замечание как «требует ручной проверки» с обоснованием
   («правка ломает mvn-сборку: <ключевая строка ошибки>»). Продолжай с остальными замечаниями —
   одна сломанная правка не должна блокировать остальные.
4. Если сборка **упала не из-за правок этого скилла** (пре-existing failure) — останови
   выполнение и заверши `AO_TASK_FAILED` с сообщением «mvn-сборка упала до моих правок, ключевая
   строка ошибки: <…>». Не помечай замечания как исправленные при красной сборке.
5. Если сборка **зелёная** — переходи к шагу 4.

## Шаг 4. Пометить замечания исправленными в `review-report.md`

Для каждого замечания, которое скилл успешно исправил в шаге 2 и подтвердил сборкой в шаге 3,
вставь в `review-report.md` под строкой `### N. ...` (перед блоком `**Файл:**`/`**Проблема:**`/
`**Сценарий:**`) строку статуса:

```markdown
✅ исправлено <YYYY-MM-DD> (<краткое описание правки в 3-7 словах>)
```

Используй текущую локальную дату контейнера. Краткое описание — что именно поменялось, не
пересказ замечания (например: «добавлен `@PreAuthorize` на endpoint», не «исправлена безопасность»).

Для замечаний, помеченных в шаге 2 как «вне scope» или «требует ручной проверки», вставь
соответствующий маркер с обоснованием.

Затронутые замечания — **только** из списка шага 1.4. Остальные замечания (уже помеченные
✅/🚫/⚠️ от прошлых запусков этого скилла) не трогай.

## Шаг 5. Обновить сводку в `review-report.md`

В секции `## Итог` отчёта обнови счётчики и вердикт:

- `Найдено: <общее число замечаний>` — из раздела `## Находки` + `## Второстепенные замечания`.
- `Исправлено: <число замечаний со статусом ✅>` — посчитай по всему файлу.
- `Осталось: <Найдено − Исправлено − Вне scope>`.
- `Сборка: ✅/❌` — по результату шага 3.

Если `Осталось: 0` и нет замечаний со статусом «требует ручной проверки» — финальный вердикт
`Готово к повторному ревью`. Иначе — `Требует повторного ревью после правок` (если ещё остались
не исправленные) или `Готово к ручной проверке` (если остались только «требует ручной
проверки»).

## Шаг 6. Сообщить пользователю

Кратко (2-4 предложения): сколько замечаний исправлено, сколько осталось, результат сборки,
путь к обновлённому `review-report.md`. Не дублируй содержимое отчёта в чат целиком.

## Важно

- Код правится **только** по замечаниям из `review-report.md`. Никаких «заодно» правок.
- Замечание считается исправленным **только** после зелёной сборки. Красная сборка — статус
  «требует ручной проверки», не «исправлено».
- При наличии любых сомнений (устаревшая ссылка на строку, неоднозначный сценарий, правка
  пересекается с чужим кодом) — не угадывай, помечай как «требует ручной проверки» с
  обоснованием. Это лучше, чем вносить неверную правку.
- Не делай `git add`/`git commit`/`git push` — это работа следующего шага конвейера.
- `AO_TASK_DONE` — успех (все замечания либо исправлены, либо явно вне scope, сборка зелёная).
- `AO_TASK_FAILED` — неустранимая ошибка: красная сборка до правок, detached HEAD, нет
  `review-report.md` при этом и т.п.

## Маркер завершения (для запуска из pipeline)

По завершении работы выведи в отдельной строке ровно
`AO_TASK_DONE` (если всё удалось) или `AO_TASK_FAILED` (если не удалось выполнить). Ничего не
пиши после этой строки.
