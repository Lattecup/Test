# /spec-review-triage — Триаж замечаний ревью: собрать решения пользователя

Скилл читает `specification/increment/{раздел}/{ticket}/review-report.md`, по каждому
замечанию **по одному** задаёт пользователю вопрос с вариантами решения (правка / отклонение /
«вне scope»), и после того как все ответы собраны — записывает принятое решение в каждое
замечание отчёта. Код при этом **не меняется**: правки делает отдельный шаг
`spec-repair-review-fails`.

**Использование:** `/spec-review-triage --release=02.009.00 --ticket=AO-595` |
`/spec-review-triage --ticket=AO-595`

`$ARGUMENTS` — обязательный флаг `--ticket=` и опциональный `--release=` (AO-313: без `--release=`
артефакты лежат в `develop/{ticket}/`). Если `--ticket=` отсутствует — остановись и сообщи об
ошибке, не пытайся определить ticket каким-то другим способом (включая имя текущей ветки).

## Строгие ограничения

- **Не правь код.** Никаких `Edit`/`Write` в `java/`, `frontend/`. Скилл только собирает решения.
- **Не правь `specification/absolut/**`, `intent.md`, `increment.md`, `index.md` тикета.** Правится
  только `review-report.md` — и только блоками решений.
- **Не коммить и не пушь.** Не делай `git add`/`git commit`/`git push`.
- **Не переключай ветки** (`git checkout`/`switch`/`worktree add`).
- **Не обращайся к remote** (никаких `fetch`/`pull`/API Gitverse/GitHub).

## Шаг 0. Разобрать аргументы и проверить окружение

1. Извлеки `--release=` (опционально) и `--ticket=` (обязателен). Если `--ticket=` нет — ошибка.
2. Раздел = `--release=<version>` либо `develop` (AO-313).
3. Прочитай `specification/increment/{раздел}/{ticket}/review-report.md` и
   `specification/increment/{раздел}/{ticket}/increment.md` (чтобы понимать контекст замечаний).
4. `git rev-parse --abbrev-ref HEAD` — если detached, сообщи и остановись (`AO_TASK_FAILED`).
5. `git status --short` — зафиксируй исходное состояние (правок кода не будет, но отчёт
   изменится — незакоммиченный diff `review-report.md` в конце и будет результатом скилла).

## Шаг 1. Собрать каталог замечаний

1. Если `review-report.md` отсутствует — заверши `AO_TASK_DONE`: разбирать нечего.
2. Найди все замечания в секциях `## Находки` и `## Второстепенные замечания`. Находки — это
   подзаголовки `### N. ...` с блоками `**Файл:**`, `**Проблема:**`, `**Сценарий:**`,
   `**Исправление:**`. Второстепенные — нумерованный список `1. **Краткое имя.** ...`.
3. Пропусти замечания, у которых уже есть маркер принятого решения (см. формат шага 4):
   `📌 решение:`. Их не переспрашивай.
4. Для каждого замечания прочитай реальный код в указанном `path:line` (через `Read`) — вопрос
   пользователю должен содержать проверенный контекст, а не текст отчёта вслепую.

## Шаг 2. Опрос пользователя — по одному замечанию за ход

Порядок: сначала `## Находки` (блокирующие), затем `## Второстепенные замечания` (по возрастанию
номера).

Для **каждого** замечания — ровно один вопрос. Формат ответа:

```
AO_QUESTION
{"question": "<текст вопроса с контекстом: файл, суть проблемы>", "options": ["<вариант 1>", "<вариант 2>", ...]}
```

Требования к вопросу:

- Текст — на русском, с указанием файла/строк и сути проблемы в 1–2 предложения.
- `options` — 2–4 варианта, **включая** вариант отклонения: `Не исправлять — пометить «вне scope
  этого скилла»` (или «оставить как есть», если замечание необязательное и правка не нужна).
- Варианты правки формулируй конкретно: что именно меняем (файл, метод, суть), а не «исправить
  баг». Если правка требует выбора между API-дизайнами — перечисли варианты и дай выбрать.
- После блока `AO_QUESTION` **не пиши больше ничего** — ход заканчивается, пользователь ответит
  следующим ходом.

Ответ пользователя может быть:
- выбором одного из вариантов;
- свободным ответом («делай как предложил» и т.п.) — тогда трактуй как согласие с лучшим
  вариантом, при неоднозначности задай уточняющий вопрос обычным текстом;
- отказом отвечать на конкретное замечание — тогда по умолчанию фиксируется «вне scope».

Собирай все ответы, **не переходя к правкам и не записывая в отчёт** до тех пор, пока не
получен ответ на каждое замечание из шага 1.

## Шаг 3. Записать принятые решения в `review-report.md`

Для каждого замечания, по которому получен ответ, вставь строку статуса **сразу под
заголовком замечания** (для находок — под строкой `### N. ...`, для второстепенных — под строкой
`N. **...**`), перед блоком `**Файл:**`/`**Проблема:**`:

```markdown
📌 решение: <краткое описание принятого решения в 3-10 слов>
```

Формат по типам решений:

- правка будет сделана — `📌 решение: исправить — <что именно меняем>`;
- отклонение — `📌 решение: вне scope — <обоснование в 3-10 слов>`;
- «оставить как есть» — `📌 решение: оставить без изменений — <обоснование>`.

Используй **локальную дату контейнера** в конце строки:
`📌 решение: исправить — удалить мёртвую перегрузку scheduleAfterCommit (2026-11-11)`.

Замечания, уже имеющие `📌 решение:`, не трогай. Никаких других правок в отчёте не делай:
блоки «Сборка и тесты», «Изменённые файлы», «Итог» не переписывай — итог обновит шаг
`spec-repair-review-fails`.

## Шаг 4. Сообщить пользователю

Кратко (3–6 предложений): сколько замечаний разобрано, сколько к правке, сколько отклонено,
перечень отклонённых с причинами, путь к обновлённому `review-report.md`. Не дублируй отчёт целиком.

## Важно

- Скилл **не коммитит** и **не пушит** — изменённый `review-report.md` остаётся незакоммиченным.
- Решения фиксируются **дословно по смыслу ответа пользователя**, а не по формулировке из варианта.
- Если по замечанию нужен ответ, которого нет среди заранее известных вариантов, — задай обычный
  текстовый вопрос (без `AO_QUESTION`) и дождись ответа.
- Никаких правок кода в этом скилле.

## Маркер завершения (для запуска из pipeline)

По завершении работы выведи в отдельной строке ровно `AO_TASK_DONE` (все решения собраны и
записаны) или `AO_TASK_FAILED` (нет отчёта, detached HEAD, отсутствует `--ticket=`). Ничего не
пиши после этой строки.
