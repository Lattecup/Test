# Комментарии и JavaDoc

[← Назад](index.md)

Правило применяется ко всем комментариям в коде — обычные `//`, блочные `/* */`,
Javadoc и их аналоги в других языках (TSDoc/JSDoc и т.п.).

- Язык — **русский**. Без исключений для нового кода
- **Лаконично**: одна-две строки максимум, без воды
- **Без исторической справки**: никаких `AO-227 Part 1 — ...`,
  `pre-AO-227 ...`, `AB-164 fix ...` и подобного — комментарий описывает код
  «как есть», а не «как было» или «почему так решили»
- Только описание того, что метод/класс/поле делает, и только если имя само по
  себе недостаточно очевидно
- Если имя говорит само за себя — комментарий не нужен

## Что не писать

- Пересказ кода строка за строкой (это и так видно из самого кода)
- Ссылки на задачу в трекере (`// AO-XXX: ...`) — для этого есть файл инкремента
  и commit-сообщение
- «Исправлен баг с N» / «по следам ревью» — это про коммит/PR, не про код
- «Раньше делали так, теперь так» — описание текущего поведения, не истории
  правок

## Что писать

- Что делает метод/класс, если это не очевидно из сигнатуры
- Какие у него предусловия/постусловия, которые нельзя выразить типом
  (например, «ожидает уже отвалидированный `Dto`», «потокобезопасен»)
- Почему именно так реализовано, если выбор между альтернативами не очевиден
  (но это обоснование решения, не история — см. также раздел
  «Обоснование решений по результатам разработки» в файле инкремента)
